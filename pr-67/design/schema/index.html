    The schema¶

    One schema per record, and manifest.json is how it is written down — the two words name the same thing, the file and the object.

    class Dimension(BaseModel):
    """One axis attribute data may vary over."""

    dtype: str  # the axis labels' type
    within: frozenset[str] = frozenset()  # labels unique only within these dims
    unit: str | None = None  # what the labels measure, if anything
    description: str | None = None  # what the axis is, in prose


class AttributeSpec(BaseModel):
    """What shape one attribute's data may take."""

    dtype: str  # value column type
    dims: frozenset[str] = frozenset()  # what addresses it: dims and groups
    default: Any | None = None
    default_by: dict[
        str, dict[str, Any]
    ] = {}  # categorizing property -> category -> default
    breakpoints: bool = False  # may carry a piecewise-linear curve
    unit: str | None = None  # what the values measure
    description: str | None = None  # what the attribute is, in prose


class PropertySpec(BaseModel):
    """One value per label of its subject, describing the label."""

    dtype: str
    default: Any | None = None
    default_by: dict[str, dict[str, Any]] = {}
    unit: str | None = None
    description: str | None = None


class Group(BaseModel):
    """Which tuples over several dims exist: a sparse subset of a dim product."""

    over: dict[str, str]  # coordinate name -> the dim it draws labels from
    into: str | None = None  # each `over` tuple carries exactly one label of it
    description: str | None = None


class Trait(BaseModel):
    """A bundle of attributes, and which categories and labels carry it."""

    attributes: frozenset[str] = frozenset()
    on: dict[str, frozenset[str]] = {}  # one categorizing property -> its categories
    switch: str | None = None  # attribute deciding it per label; joins `attributes`
    description: str | None = None


class Schema(BaseModel):
    version: int  # bumped by any change to the declarations

    dimensions: dict[str, Dimension]
    attributes: dict[str, AttributeSpec]  # flat: one attribute, one spec
    results: dict[str, AttributeSpec]  # what a solve computes, governed apart
    properties: dict[
        str, dict[str, PropertySpec]
    ]  # subject dim or group -> name -> spec
    groups: dict[str, Group]
    traits: dict[str, Trait]  # the only thing that narrows a name to some categories

    # Which dims a layer may patch value by value; absent for a record with no
    # layers, since nothing overrides anything.
    partial: frozenset[str] | None = None

    meta: dict[str, Any] = {}  # opaque; the package never interprets it

    partial is the only layering-specific part, and so the only optional one. Everything else describes the data and is always present.

    attribute is VARCHAR, and no dim or property name means anything to this package: those vocabularies belong to a modelling framework, and this package knows none. A category is typed as the schema declares it, which is a record's own statement rather than a framework's — so a category the schema declares but no tool recognises reads back fine and is reported by the tool that cannot build it, not rejected inside the fold.

    meta is where a framework's own top-level data goes — network attributes, coordinate reference system, free-form metadata. It is stored and never interpreted, since none of it describes the dimensioned data.

    Dimensions¶

    Every dim is declared: a record with region, technology or vintage needs no code change, and dtype is the axis's own property.

    A Dimension declares the axis's shape — its type and its nesting. It does not declare which dims an attribute varies over (that is per attribute), nor the patch granularity, nor order, nor what describes or classifies its labels — its properties say that, and a group into it from the relation's side.

    AttributeSpec¶

    What one attribute may do over those axes:

    attributes = {
    # a capacity to build: one decision, evaluated against every scenario
    "p_nom": AttributeSpec(dtype="float64", dims={"entity"}),
    # an availability profile: varies over time, and per scenario
    "p_max_pu": AttributeSpec(dtype="float64", dims={"entity", "scenario", "timestep"}),
    "marginal_cost": AttributeSpec(
        dtype="float64", dims={"entity", "scenario"}, breakpoints=True
    ),
    # addressed by a group rather than by the entity axis
    "efficiency": AttributeSpec(dtype="float64", dims={"connection", "timestep"}),
    # addressed by an axis alone: a weighting belongs to no entity
    "objective_weighting": AttributeSpec(dtype="float64", dims={"snapshot"}),
}

    Flat, one spec per attribute, with categories subscribing rather than owning. The nesting this replaces said an attribute belongs to an entity type, which is false in both directions: objective_weighting has no type, and p_max_pu was three identical specs under Generator, Link and StorageUnit.

    The storage already disagreed with the nesting. inputs/p_max_pu.parquet holds every type's rows in one file with one value dtype, so two types declaring one attribute with different dtypes was expressible in the schema and unrepresentable on disk — a silent wrong read that nothing rejected. Flat declaration makes it unrepresentable instead, which is the stronger form of the same guarantee: one attribute, one spec, one file, one dtype.

    dims is the only addressing mechanism, and it names dims and groups alike, resolved by one rule: a name is the dim of that name if one is declared, and otherwise the group of that name, carried as one column. Whether a coordinate is the entity axis, a group or a plain axis changes where the labels come from, not how the attribute is declared or stored. There is no bus field: an attribute is a connection attribute because its dims name the connection group, which is what lets a second group exist without a second field.

    dims is also what makes a scenario-varying p_nom a schema violation: a capacity is a first-stage decision, one value taken before the scenario is known, which is the point of stochastic scenarios differing only in dispatch.

    dims says only which coordinates address a value, not what kind of value it is: p_nom over entity alone is data an optimiser decides, where carrier describes the entity — so carrier is a property, and dims may name one coordinate without making an attribute one.

    breakpoints answers what a bare column set cannot: whether it may carry a piecewise-linear curve, so a curve on an attribute that takes one value is rejected on write rather than reported unbuildable later (wide and long rows).

    Every attribute is long rows in inputs/<attr>.parquet, whatever its dims — where a value lives is decided by the section a name is declared in, not by how many coordinates address it, so widening dims adds a column to the same file rather than moving it.

    default_by is a default per category, beside default (below).

    Results¶

    results is a second mapping of AttributeSpec, keyed and shaped exactly like attributes. What a solve computes is declared, not discovered: a result has a dtype, coordinates and a description like any other attribute, and reading one back needs its dtype as much as an input does — a string-valued result cast as a number is lost to TRY_CAST with nothing raised.

    It is a separate mapping rather than a flag because the two are governed differently at every point a caller touches them. A result is written to outputs/<attr>.parquet, never overlays a parent's, and may name an entity the record does not declare. An input meets attributes_for, which is the per-category vocabulary that validates a set; a result meets none of that, and keeping it out of attributes is what makes that structural rather than a condition repeated at each site. A name in both is rejected: one name is one file with one value column, so it is an input or a result and not both.

    The questions the long schema asks of a stored attribute — its dtype, its coordinates — span both, since outputs/ and inputs/ share a layout. Those go through one lookup that consults each in turn.

    A tool declares its results from the same registry it declares its inputs from. PyPSA marks them with status starting "Output", so the vocabulary is read rather than kept as a list, and an upgrade that adds a result is picked up. That is what keeps declaration from becoming a maintenance burden on the tool: the alternative — a tool attaching whatever its registry produced, unchecked — buys nothing a caller can rely on, since a consumer reading outputs/ still needs a dtype to read it at.

    Results version like inputs (versioning): removing one, changing its dtype, or narrowing its dims makes existing layers unreadable for the same reasons.

    Properties¶

    What describes one label of a dim — its type, its carrier, a coordinate on a map — is metadata rather than data, and is declared apart from it, keyed by its subject:

    properties = {
    "entity": {
        "entity_type": PropertySpec(dtype=Enum(["Bus", "Generator", "Load"])),
        "carrier": PropertySpec(
            dtype="str", default="", default_by={"entity_type": {"Bus": "AC"}}
        ),
    },
    "bus": {"x": PropertySpec(dtype="float64", unit="°")},
    "connection": {"role": PropertySpec(dtype="str")},
}

    A property is one value per label of its subject, a dim or a group, and so has no dims: it never varies along another axis. It is a column of the subject's own file — dims/<dim>.parquet, or groups/<group>.parquet for a group (where a value lives) — so entity_type is a column of dims/entity.parquet because every property of entity is, and the schema attaches no meaning to the name.

    An attribute is data: what a model reads as part of its problem and what a layer would vary. Which a name is, is the author's declaration rather than derived from its shape; a tool reads it from its registry where it can (PyPSA).

    One name, one spec, across every section. A name declared as a property and as an attribute or result, or as a property of two subjects, is refused — flags would have two answers for it. So is a property sharing a dim's or a group's name, which would collide with that coordinate's column, and a group's property sharing one of its coordinates' names, which name the tuple's fields. This is the flat-attributes argument extended to the new section. Schema.subject_of(name) and Schema.property_spec(name) find a property whatever its subject.

    The argument for the split is the properties proposal.

    Categories — an Enum property of a partial dim¶

    Any Enum-typed property of a dim listed in partial categorizes it: its values are that dim's categories along it, which a trait's on and a default_by key on. Schema.categorizing(dim) lists them in declaration order. There is no flag declaring the role and no limit of one per dim — an Enum carrier would categorize entity beside entity_type. Keying on any other property — a str one, one of a dim outside partial, or one of a group — is refused, naming the property and why.

    The two conditions are what a category needs: an Enum, so a category a trait or a default names is checked against a declared vocabulary; and the dim in partial, because only there is a dim owned and checked per label (why). A schema whose entities have no kinds declares no Enum property of entity, and nothing else about it differs.

    Category, because label already names an axis value — what add(dim, labels) takes. What a label carries is asked by its categories, the label's value of each categorizing property:

    • attributes_for(dim, **categories) — the attributes reaching dim such a label carries, narrowed by traits;
    • properties_for(subject, **categories) — the same for its properties, narrowed by the same traits; every tuple of a group carries all of its group's;
    • default_for(name, **categories) — the default of an attribute, result or property for such a label.

    A category may change. It is a property like any other, patched by set. Values a label holds for attributes its new category does not carry stay stored, but fall outside every per-category read and every broadcast, which are judged against its current categories.

    default_by — a default per category¶

    default stays the fallback; default_by maps a categorizing property to per-category overrides, on attributes and properties alike:

    "p_min_pu": AttributeSpec(
    dtype="float64", dims={"entity", "snapshot"}, default=0,
    default_by={"entity_type": {"StorageUnit": -1}},
)

    A value read unset takes the first default_by key, in declaration order, whose map lists the label's category; else default.

    • Each key reachable from the value's address. A key must categorize a dim the value reaches — entity directly, or through connection's entity field for a value over the group — and a category outside its property's Enum is refused.
    • Never on a categorizing property. A category defaulted by a category is circular; such a property takes a plain default.
    • Only the default varies. dtype, unit and description are the spec's own, which is what keeps one name one column and one inputs/ file.

    A default is never stored. record.properties and record.attributes hand over stored rows, so a consumer applies a default through default_for — the PyPSA tool does, building entity_types.

    Traits¶

    A trait is a named bundle of attributes, and which categories carry them:

    traits = {
    "investable": Trait(
        attributes={"capital_cost", "build_year", "lifetime", "capacity"},
        on={"entity_type": {"Generator", "Line", "Link", "Store"}},
    ),
    "dispatchable": Trait(
        attributes={"p_min_pu", "p_max_pu", "p_set"},
        on={"entity_type": {"Generator", "Link"}},
    ),
}

    A trait narrows; it does not grant. An attribute the schema declares is carried by every label it can address, and a trait is the only thing that cuts that down. Writing entity in an attribute's dims is what says it is per entity; declining to bundle it says it is so for every category — the same thing dims={"scenario"} already means along the scenario axis, where no subscription mechanism exists and nobody finds it surprising.

    That direction is why an attribute belonging to no type has somewhere to live at all. Under the previous shape a type subscribed and an attribute reached nothing until one did, which is what forced attributes to be nested under types and left snapshot weightings homeless.

    Whichever property each trait keys on. An attribute no trait claims is carried by every label; a claimed one by every label some claiming trait matches. A trait on entity_type: [Generator] and one on carrier: [wind], both claiming p_max_pu, give it to every generator and every wind entity.

    Schema.attributes_for(dim, **categories) and Schema.properties_for(subject, **categories) (categories) are what flags, a consumer's per-category frame and the validation of set read, so everything downstream asks one question and gets a resolved answer. A trait may bundle properties of the dim its on categorizes beside attributes, and both are narrowed alike. An attribute addressed by an axis alone is carried by no category however few traits mention it: a snapshot weighting belongs to the record.

    A trait rather than a bare list of attribute names, for two reasons. The deduplication is real: the boundaries are measured from a framework's registry rather than invented, and investable covers six types. And a trait is queryable — a consumer dispatching on "everything investable" asks the schema rather than enumerating types, which is what makes the vocabulary worth declaring at all.

    Declared, not inferred. No framework ships a trait registry to read, so the mapping from its component registry to traits is authored and maintained. That cost is the price of the vocabulary being useful to something other than this schema.

    Only a categorizing property may scope a trait, and one per trait. on names one categorizing property and categories of it; the schema rejects any other key, because a trait scoped to, say, country would make an attribute's vocabulary depend on a relation — which attributes an entity carries would follow from what its bus maps to, a join every caller of attributes_for treats as answerable from a label's own categories. A trait spanning two properties is two traits.

    A trait with an empty on narrows nothing: it is a bundle for a consumer to dispatch on, and its attributes stay carried by every label.

    A trait may only name an attribute or property the schema declares: it says which apply, never what they are, so a name with no spec is a typo rather than a shorthand declaration. Two traits bundling one attribute is fine — they resolve to a set — since one attribute has one spec and there is nothing left to conflict.

    switch — a trait an entity opts into¶

    A trait narrows two ways: on says which categories carry it, switch names an attribute deciding it per label.

    traits = {
    "committable": Trait(
        attributes={"start_up_cost", "min_up_time", "ramp_limit_start_up"},
        on={"entity_type": {"Generator", "Link"}},
        switch="committable",
    ),
}
attributes = {
    "committable": AttributeSpec(dtype="bool", dims={"entity"}, default=False),
}

    The two never interact: on first, then switch. A trait with neither reaches every label; a switch needs an on, and is addressed by exactly the dim its on property categorizes — the dim it decides the trait per label of.

    The switch is an ordinary attribute, with a dtype, a default and long rows in inputs/ like any other (where a value lives). bool is the dtype the proposal admits; an Enum switch selecting among several traits is deferred. Its default decides the unset case, and false keeps the bundle off every entity that predates the trait.

    It joins the trait's attributes on its own, folded in at parse rather than listed by the author, so a consumer asking what committable bundles gets the switch with the rest. Being in the bundle it would otherwise be narrowed by its own trait, which nothing could then turn on — so it is in attributes for discovery and out of the narrowing.

    attributes_for is unchanged by it. A switched trait's attributes are carried by the category, because the question it answers is which attributes a generator may have; the switch narrows which entities carry a value, which is a question about data. So the switch is a validation and query mechanism rather than a change to the vocabulary. What it is declared for — rejecting a value set on an entity whose switch is false, and asking which entities a trait reaches — reads the switch column, and neither is wired up yet: the declaration lands first, the checks that read data after. Whether attributes_for grows a per-label counterpart is open.

    Groups¶

    A group declares which tuples over several dims exist: a sparse subset of a dim product, with its own order.

    groups = {
    "connection": Group(over={"entity": "entity", "bus": "bus"}),
    "corridor": Group(over={"from": "bus", "to": "bus"}),
    "bus_country": Group(
        over=["bus"], into="country"
    ),  # functional: one country per bus
}

    Not an axis of labels: a dim declares one, a group declares which combinations are there, which no axis can say because the product is sparse — an entity attaches to two buses out of a thousand. As a coordinate, though, a group is a dim whose axis is the resolved group: it broadcasts, and is partial or owned whole, by the rules a dim follows.

    over maps coordinate name → dim rather than naming a bare set of dims, because two coordinates may draw on the same axis: a corridor between two nodes is (from, to), which a set could not spell. A list is sugar for the dict with identical keys and values, so over=["bus"] is over={"bus": "bus"}.

    An attribute over a group carries the group as one struct column named for the group, a field per key coordinate in over order:

    inputs/efficiency.parquet       connection STRUCT(entity, bus) | timestep | attribute | breakpoint | value
inputs/flow.parquet             corridor STRUCT("from", "to")  | timestep | attribute | breakpoint | value
inputs/marginal_price.parquet   bus | timestep | attribute | breakpoint | value

    The column's name says which group constrains the row, so two groups may share a coordinate set without ambiguity, and a group's coordinate never takes the column of the dim it draws on — bus inside connection is not the dim bus beside it.

    A group file is keyed by the same column: groups/connection.parquet is connection STRUCT(entity, bus) | role, as dims/bus.parquet is keyed by bus, so a row and the group it names meet on one column with nothing packed between them.

    A group in dims resolves to itself, so dims={"connection", "timestep"} gives the columns connection | timestep, groups first — addressing states the full rule. The fold's key therefore does not vary per attribute: partial_dims is one fixed tuple, exactly the dims and groups partial names.

    An attribute may not name a group beside a dim its key coordinate is named for. dims={"connection", "bus"} is rejected: the row would hold the bus twice, free to disagree — the same "keyed twice over" rule into states.

    A group's file columns are not declared here. They are its properties, declared under the group's name — PyPSA's role on a connection is properties: {connection: {role: ...}}, declared by the tool whose vocabulary the word is — and an attribute over the group is long rows in inputs/ keyed by the struct (where a value lives). Declaring them a second time on the Group would be two ways to say one thing, disagreeing eventually. A group is never categorized: its tuples carry every property it declares.

    A group column broadcasts, its axis the resolved group. A NULL struct means every tuple of the group, expanded against groups/<group>.parquet as a NULL dim is against dims/<dim>.parquet (the broadcast rule). A group value is a whole tuple or NULL. A struct with some fields NULL names a tuple no group row matches, so it is refused wherever a row comes in — set, add_group and the writer. A group is keyed where a dim is: in the fold key where partial names it, owned whole otherwise, so a layer touching one connection's value then restates the attribute's whole extent along the group. The dims a group draws on broadcast on their own: bus is an ordinary axis whose NULL means "every bus", so a per-bus marginal_price beside a connection group may hold one value for all of them. Every group is such a coordinate (Schema.group_columns).

    Connections are one instance, not a structural category: Group(over={"entity": "entity", "bus": "bus"}), with role a property of it. bus is accordingly one coordinate of one group rather than a column the format fixes, and neither word appears in the record layer — connection is whatever a schema calls it, and role is a tool's declaration.

    into — a group that classifies¶

    into names the dim a group is functional into: each tuple of over carries exactly one of its labels. bus_country over [bus] into country says every bus is in one country.

    It is a declaration a bare group cannot make. A group can only happen to be single-valued, which leaves a duplicate row a data error the schema has no name for; into names it, so the constraint is declared and checkable on write. No existing system declares it — GAMS's map(b,c) is a set over a tuple of sets with single-valuedness left to convention, and a duplicated b silently double-counts — which is the argument for the field rather than against it, a schema whose purpose is making shape checkable having no reason to inherit that gap.

    into must name a declared dim. That is what keeps the axis file, and the axis file is the whole of what a functional group has over a bare tuple set: dims/country.parquet gives country its order and somewhere for a per-country CO2 budget to live.

    into is sugar, resolved once at parse. It is a plain column beside the key, so groups/bus_country.parquet is bus_country STRUCT(bus) | country and is keyed by its struct exactly as connection is, and no read path, file layout or fold key branches on whether a group has one. The field is retained for the three things that still need it: the uniqueness constraint (the key being the coordinates minus into), a consumer's aggregation, and round-tripping the manifest — writing back over: [bus, country] where the author wrote into: would silently rewrite their schema.

    It may not key an attribute alongside what it maps from. dims={"bus", "country"} is rejected: into says the country follows from the bus, so the row would be keyed twice over and the two free to disagree.

    Nothing assumes one coordinate. over: [bus, scenario] with into: country — a bus whose country varies per scenario — is allowed, the constraint being per-tuple already. It costs nothing in storage because every group is a file.

    Addressing: dims: [X]¶

    An attribute names a group in its dims exactly as it names a dim, and one rule resolves both:

    X is the dim X if one is declared, and otherwise the group X, carried as one struct column of its name.

    "efficiency": AttributeSpec(dims={"connection", "timestep"}),  # connection | timestep
"co2_budget": AttributeSpec(dims={"country"}),  # country: the dim

    A group with no dim of its name has no other spelling, so naming it is the only way to declare an attribute over it; coordinates_of lists the attribute's groups first, then its dims in declaration order.

    A group may not share a dim's name: a group is carried as a column named for it, so sharing a dim's name makes two columns one name. A functional group is named for the relation rather than the axis it classifies into — bus_country into country — and the schema's error says so.

    Existence does not vary along a dim¶

    An entity exists or it does not. There is no declaration making membership vary per value of an axis — no generator present in scenario high and absent from low — so dims/entity.parquet holds one row per entity and a tombstone removes it whole.

    That is a deliberate narrowing. An earlier Dimension.keys declared exactly this, putting the dim in an entity table's key so an entity existed per scenario; it is gone, with nothing in its place, because what it should mean is unsettled once connections are one group among several rather than a fixed second entity table.

    What remains is the distinction that was doing the useful work: a value may vary along an axis where the thing may not. A stochastic network holding a different capital_cost per scenario is expressing exactly that, and it is an attribute with dims = {"entity", "scenario"} — long rows in inputs/, not an entity that exists twice. Where a value lives already places it.

    within — an axis inside an axis¶

    A dim whose labels identify a point only within another dim's value. Multi-period time is the case: the axis is a (period, timestep) pair, so t1 alone names nothing and two periods may hold different timesteps.

    dimensions = {
    "period": Dimension(dtype="int64"),
    "timestep": Dimension(dtype="datetime64[us]", within={"period"}),
}

    within makes timestep.parquet carry a period column, and the axis key (period, timestep) rather than timestep. It is on Dimension because nesting is structural — true of the data however stored, so a directory record needs it exactly as much as a layered one.

    A set, because two different things could each be one parent:

    • Chained — timestep in period in horizon. Each dim names its immediate parent and the chain is walked, giving (horizon, period, timestep).
    • Several direct parents — timestep identified only within a (period, stage) pair, where neither contains the other. This is what a multi-stage stochastic program with investment periods looks like.

    So the axis key is (*parents, dim), parents in declaration order. Every name in within must be a declared dim, and the nesting graph must be acyclic.

    Distinct from AttributeSpec.dims despite the similar shape: dims names independent coordinates — a value exists at each combination and the set never chains — whereas within qualifies a label and is transitive, so naming period pulls in period's own parents.

    The inner dim is named for the thing it indexes (timestep) rather than for the pair (snapshot), because once nesting exists the pair needs its own name: a framework consuming the record calls (period, timestep) a snapshot.

    within is not into¶

    Both are acyclic and both relate one dim to another. They mean opposite things:

    • within names a dim's parents: its label set is scoped per parent, so t1 in 2015 and t1 in 2020 are different points and the axis key is (period, timestep).
    • into names the dim a group classifies its coordinates by: one flat label set, each over tuple picking one of its labels. country is not scoped by bus; it is a partition of buses, and its axis key is country alone.

    Nesting versus classification. within cannot express country, and a functional group cannot express timestep. within stays on Dimension because nesting is a property of the axis itself; into is on Group because a classification is a relation, with rows.

    A functional group is single-valued by declaration rather than by construction, which is the whole of what into adds — a many-to-many classification is an ordinary group, and expressible as one.

    A chain is not denormalised. bus→state→country is two group files, never a country column on dims/bus.parquet. Two files asserting bus→country would let a layer restating the states leave every bus's country stale with nothing to detect it, so the chain is a join over two files — which a file per group gives for free, a layer restating a group restating exactly one file.

    The record does not resolve across levels. An attribute over country is handed back keyed by country; projecting it down to buses is a join through the group, and that is the consumer's work. The fold learns no new operation.

    Membership could not vary along a classification either, if it varied along anything: whether an entity exists in Germany is already settled by its bus and that bus's country, so there would be no freedom for it to vary independently (existence does not vary).

    partial — the granularity of an override¶

    Everything is overridable; a layer exists in order to override. The remaining question is at what granularity along each axis, and it splits from AttributeSpec's question because the two are properties of different things:

    • Which dims may this attribute vary over at all? — per attribute. p_max_pu varies over scenario and timestep; p_nom over neither. AttributeSpec.dims.
    • May a layer patch individual values along this axis, or must it restate the axis whole? — per dimension. scenario is patchable value by value; timestep is not, for any attribute. schema.partial.
    partial = {"scenario"}  # timestep absent, so a patch restates the series

    A dim outside partial is one a layer owns entirely once it touches it: overriding one timestep of p_max_pu means carrying that entity's entire series, because a partial series would resolve across two layers and produce a curve with a hole. The reason is a consumer's rather than the format's — a framework that splits constant from varying data cannot receive half a series — which is why it belongs to the axis: it is true of every attribute varying over it.

    The dims a layer owns an attribute per follow from the declarations:

    owned_per(attribute) = attribute.dims ∩ partial_dims
partial_dims         = broadcast coordinates ∩ schema.partial

    partial_dims is the fold key: exactly the broadcast coordinates — dims and groups — declared partial. No dim is in it by name; a schema patching entity by entity lists entity, as PyPSA's {entity, scenario, connection} does. A dim a group draws on is a broadcast dim like any other, so a layer patching a per-bus marginal_price one bus at a time needs bus in partial; a layer patching one connection's efficiency needs connection there, and the connection's bus is patched with it, inside the connection column. Neither is needed for the group itself: a dim a group draws on may stay out of partial, a removed label's tuples being tombstoned with it. So p_max_pu is owned per entity and per scenario — timestep is not partial, so a patch to one hour restates that entity-scenario's whole series; marginal_cost per entity and scenario; p_nom per entity, once across everything else.

    Two things this buys. The schema can distinguish p_max_pu from p_nom, which a dim-level flag cannot: that would say every attribute is owned per scenario, including those a scenario must not change. And a p_nom row carrying a non-NULL scenario becomes a write-time violation rather than something the NULL-broadcast rule absorbs — a first-stage decision quietly turned into a per-scenario one is the error worth catching.

    What the fold does with this is unchanged: the inputs key is one fixed tuple over all attributes, and an attribute not varying over a dim writes NULL there. So the declarations constrain and validate; they do not make the key vary per row.

    An axis file is owned the same way, and the properties it carries do not argue for adding it — save one: a dim with a category must be in partial, since only there is it checked per label. Outside partial, a layer touching an axis restates it whole — every label, with the properties attached to them — because a layer holding one label is not saying the others are unchanged but that they are not there: the fold keys by the axis key, so what this layer carries is what the axis has here. That is the same "no half-owned extent" rule a series obeys, applied to a set of labels rather than a curve.

    Keep it small. Every partial coordinate widens the fold key, and the key is paid for by every read of every attribute. The cost of leaving one out is paid once per edit and bounded by the axis or group; the cost of putting it in is paid by every read forever. So partial names only the dims and groups a layer genuinely patches value by value — entity, scenario and connection, not timestep or bus.

    Names¶

    A declared dim, group, group coordinate, attribute, result or property name becomes a column, beside the columns datarecord writes itself. Schema refuses one at load that could not stand there, naming it and the reason:

    • " or .. A name reaches DuckDB as a column reference, which reads a.b as column b of table a and cannot spell a " at all. A space, mixed case, a keyword or a leading digit are fine: those quote.
    • A column the format writes. attribute, breakpoint and value on every long row, deleted as a tombstone, varies, broadcast, breakpoints and layer_uuid in the owner map, and order_key on a resolved frame. Ignoring case, as DuckDB resolves a column name. A collision is silent otherwise: a dim named value gives the long file two columns of one name, and one named deleted reads every label as a tombstone, dropping its rows with nothing reported.
    • A leading _. The prefix of every scratch column a fold adds and drops, so that set can grow without growing this list.
    • Two spellings differing only in case. DuckDB resolves Bus and bus to one column, so a schema declaring both would have one read the other's values. One spelling declared twice, as when a group's coordinate is named after the dim it ranges over, is a single column and fine.

    Entity names and labels are data, never identifiers, so none of this constrains them.

    No dim or property name is reserved — not entity, not entity_type: a schema declares them like any other, so neither can be taken by surprise. What one name may not be twice over is a section's rule, not this list's.

    One schema per record¶

    Not one per layer. A directory record's schema is manifest.json in the directory; a layered record's lives beside the layers, not inside any of them:

    record-root/
├── manifest.json               # the schema — one, for the whole tree
└── layers/<uuid>/              # a layer: dims/, inputs/, outputs/ — no manifest
    └── resolved/               # caches (owner map, resolved dims)

    A schema is not layered data. Folding it would let a layer change what p_nom means — its dtype, which dims it varies over — which is not a patch to data but a redefinition of the thing being patched, and it makes the schema unknowable without walking the ancestry. One schema makes it a property of the record, validatable before anything is read and stated once for a hundred-layer tree.

    The cost is that adding an attribute amends the root schema rather than shipping inside the layer that introduces it. That is the right trade: a new attribute is a schema change, and one buried several layers deep is exactly what should be visible.

    A layer directory therefore holds only data, which is what keeps it a plain parquet directory readable by a tool that knows nothing about layering.

    Which of the two a directory is decides what it is read under. A standalone record carries its own manifest.json, so Workspace.at(uri) reads that file and the record answers the same through any workspace — it is one whole record, and may well be opened from somewhere that knows nothing about it; at refuses a directory without one. Its manifest also carries an id, a UUID ws.write mints, beside the schema's keys rather than wrapping them, so the file still parses as the schema. The id is the record's layer id, which keys the fold tables a workspace shares: derived from the URI instead, a record deleted and written again there, or a relative path read from another working directory, would be served the folds of the record before it. at refuses a manifest without one. A tree's manifest needs none, its revisions naming its layers. A single layer directory carries none, so it is read through its store, store.layer(id), under the manifest beside the tree it belongs to.

    An edit changes neither. A WorkingRecord is one more layer over its base, and a layer declares nothing — so it reads under whatever its base's schema is, standalone or not. A staging area that could redeclare would be the layered-schema case above, arriving by a different door.

    Versioning¶

    One schema outlives many layers (above), so a change to it meets data written under the previous one. version records which schema a record's layers were written against, and what matters is which changes existing layers survive.

    Compatible — old layers stay readable, version bumps and nothing else happens:

    • adding an attribute, a property, a category, a trait, or a group — none changes the owner map's key, which only partial widens
    • adding a dim no existing attribute varies over
    • a category carrying a further attribute, whether by a trait claiming it for that category or by no trait claiming it
    • widening an AttributeSpec.dims: rows that set fewer dims still decode, since an unset dim is NULL and NULL means "all values" (the broadcast rule)
    • adding to partial: ownership becomes finer, and an existing layer's rows are simply owned at the coarser granularity they were written with
    • changing a unit or description, which describe the data without deciding how any row decodes

    Incompatible — existing rows would decode differently, or not at all:

    • narrowing dims, since a row setting a now-undeclared dim has no valid reading
    • changing a dtype, which includes dropping a category from an Enum
    • moving a name between properties and attributes, or between subjects: it moves the file the value is read from
    • removing from partial: a layer that patched one value along that axis is now a partial override of an axis owned whole, which is exactly the hole partial forbids
    • changing within, since the axis key changes shape
    • a category ceasing to carry an attribute, whether by dropping it or by a trait no longer claiming it for that category: its rows are still in the file, now with no valid reading for that category

    Adding a functional group is compatible in the same sense adding any group is: the record gains a file, and until some layer writes it every coordinate reads as unclassified — no row, which is what "no country assigned" means anyway.

    The compatible changes are those where NULL already means what the new schema needs it to mean, so the broadcast rule absorbs them without touching a row.

    An incompatible change therefore needs the layers rewritten rather than the schema edited, which for a layered record means flattening it to a standalone directory under the new schema. A reader encountering a version it was not written for should refuse rather than guess, since every failure above is silent.

    unit and description¶

    A Dimension, an AttributeSpec and a PropertySpec may each carry a unit and a description. Neither is interpreted: no conversion, no dimensional analysis, no validation that MW and kW are not being added. They are stored, read back, and handed to whatever displays or documents the record.

    They belong in the schema rather than in meta because they describe the dimensioned data — which is exactly the line meta is on the other side of. A unit is a property of an attribute in the same way its dtype is, and a consumer asking "what is p_nom and what is it measured in" should not have to know a framework's own metadata layout to find out.

    None means undeclared, not dimensionless. A quantity that genuinely has no unit is "" — the distinction matters to a renderer choosing between showing nothing and showing an empty unit, and to a later pass that wants to find what is still undocumented.

    A dimension's unit describes what its labels measure, which is only sometimes meaningful: a vintage axis labelled in years or a distance axis in km has one, while scenario and timestep do not — a timestamp is not a quantity. description applies to any axis.

    Neither field changes how a row decodes, so adding or editing one is a compatible change.
